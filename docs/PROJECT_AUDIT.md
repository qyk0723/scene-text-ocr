# P0 — 阻断 / 影响结论正确性

## P0-1 检测评测未实现 ICDAR2015 的 do-not-care 协议

### 事实

对 `data/icdar2015/detection/test/gt/` 全部 500 个文件逐行统计（共 5230 行）：

| 转写字段 | 框数 | 占比 |
| --- | --- | --- |
| `###`（无效区 / do-not-care） | **3153** | **60.3%** |
| 真实文本（`Please`、`residential` …） | **2077** | **39.7%** |

GT 是官方原版（例如 `gt_img_100.txt` 里保留了官方著名的 `Refishing` 拼写错误），**并非"被剥离为统一 `###`"**。因此 `docs/evaluation_report.md:76` 的论断与数据不符，并据此放弃了一个本可实现的标准协议。

`src/evaluator/parsing.py:11-26` 只取每行前 8 个数字，**丢弃了承载该标志的第 9 个字段**；`tests/test_evaluate.py:36` 还把一行 `###` 当作合法四边形来断言——即这个丢弃是被测试固化的。

### 影响可以精确表达

设 `r_real` / `r_dnc` 为两类框各自的命中率。当前召回 = (2077·r_real + 3153·r_dnc)/5230；标准协议召回 = `r_real`。两者相比：

> **标准协议召回 > 当前召回 ⟺ r_real > r_dnc**

即只要真实文本框比无效区更容易命中，召回就一定上升。而实测两类框尺寸存在系统性差异，方向明确：

| 类别 | n | 高度 min / p25 / 中位 / p75 | 面积中位 |
| --- | --- | --- | --- |
| 真实文本 | 2077 | 9 / 23 / **34** / 54 | 2160 px² |
| 无效区 | 3153 | 5 / 16 / **23** / 38 | 875 px² |

无效区明显更小更难（高度 <15px 的比例 20.0% vs 5.2%），所以 `r_real > r_dnc` 几乎必然成立，**召回率很可能显著上升**。

但 **F1 的方向是开放的**。在"命中无效区的预测框从 TP 和 FP 中同时移除、被忽略的未命中预测未建模"的简化假设下，令 x 为落在无效区上的匹配数：

```
P(x) = (1355 − x) / (2208 − x)      R(x) = (1355 − x) / 2077
F1(x) = 2(1355 − x) / (4285 − x)

x = 0    → P 61.4 / R 65.2 / F1 63.2      （上界）
x = 702  → F1 = 36.43                      （与现状持平，即 51.8% 的匹配落在无效区）
x = 817  → P 38.7 / R 25.9 / F1 31.0      （按 60.3% 比例分布）
```

对应到命中率之比：**F1 改善的临界点是 `r_real / r_dnc ≈ 1.41`**（此时 x=702）。若两类框命中率相近（比值 1.0），F1 反而从 36.43 降到约 31。所以：**召回大概率上升，F1 升降必须实测。** 另外上式未计入"落在无效区但未命中的预测也应被忽略"这一项，计入后精确率会比表中更高。

### ✅ 已实测（2026-10-06，30 张带种子随机样本，PP-OCRv6 small）

样本：500 张中随机 30 张（种子 20261006），GT 353 框 = 真实文本 125 + 无效区 228（无效区占 64.6%）。**同一批预测框同时按两套口径计算**：

| 配置 | 旧口径 P / R / F1（现状） | do-not-care P / R / F1 | x（命中无效区的匹配） |
| --- | --- | --- | --- |

## P2-17 `crop_box` 对退化框静默返回整图

`src/pipeline/geometry.py:crop_box`。实测：

| 输入 | 结果 |

## P2-19 `deskew` 的角度估计**根本无效**（原判"有缺陷"，根因判断也有误）★已修复

`src/preprocess/enhancer.py` 原实现：

```python
coords = np.column_stack(np.where(thresh > 0))
angle = cv2.minAreaRect(coords)[-1]
angle = -(90 + angle) if angle < -45 else -angle
```

**原判**：认为是"抗锯齿/杂点决定了 minAreaRect 的极值"，建议改用
`findContours` + 过滤小连通域。

**实测推翻了这个判断**：我按该建议实现后**没有修好**——在注入已知旋转的验证里，
新旧实现的估计值都是 `-90` / `0` 这类量化值。真正根因有两条：

1. **`cv2.minAreaRect` 的角度按"宽高谁更长"而模 90° 歧义**：同一个矩形可能报成 `a` 或 `a-90`，
   而 `-(90 + angle) if angle < -45 else -angle` 只能处理其中一种情形。
2. 对**整页前景点集**取一个最小外接矩形，拟合出的其实是**整页文本块的外接矩形**，
   通常与图像轴对齐，与文字方向无关。

实测（6 张单行裁剪图 × 4 个已知角度）：旧实现带符号误差均值 **−59.52°**、绝对误差 **59.52°**。
即它不是"转得不准"，而是**按一个无意义的角度乱转**。

**✅ 已换成投影轮廓方差法**（文本行与图像行对齐时逐行前景像素数分布最尖锐）：
−15°~15° 上粗搜 1° + 细搜 0.1°，先缩到长边 ≤500px。
带符号误差均值 **−0.05°**、绝对误差 **3.20°**；非零估计 100/100，|角| 中位数 10.2°（真值 12°）。

| --- | --- |

| B 倾斜校正（修复后） | 0.8177 |
| C 原图（未倾斜，上界） | 0.8534 |

# P3 — 优化与增强

## P3-26 批处理识别：机制可行，但**实测无收益，不要做**（原假设已被推翻）

**原假设（我提出，已被自己的实测推翻）**：`ocr_pipeline.py:135-139` 对每个框逐个调用 `recognizer.recognize(crop)`，39 行图 = 39 次串行推理，改成一次批量调用可获 1.5–5× 加速，是"最大的性能优化"。

**API 层面确实支持**（已读已安装源码）：`predict` 接受 ndarray 列表，`ImageBatchSampler` 按 batch_size 切片，`TextRecRunnerPredictor` 返回 dict-of-lists，`apply()` 按索引拆回。**实测也确认批量输出与逐张完全等价**（39 条对 39 条、文本逐条相同）。

**但在本机实际的运行配置下，批量一致更慢**（`run_mode='paddle'`、CPU、39 张 32×200 合成裁剪图，已预热）：

| batch_size | 1（逐张） | 2 | 4 | 8 | 16 | 39 |
| --- | --- | --- | --- | --- | --- | --- |
| 耗时 (s) | **5.27** | 9.00 | 7.01 | 6.05 | 6.09 | 5.70 |
| 相对逐张 | 1.00× | 0.59× | 0.75× | 0.87× | 0.87× | 0.93× |

medium 识别独立复现同一结论：串行 38.19 s vs 批量 60.29 s（**0.63×**）。**每个 batch size 都比逐张慢**，`batch_size=2` 最差。合理解释：`run_mode='paddle'` 关掉了 MKLDNN/oneDNN，CPU 上的宽 batch GEMM 没有收益，反而增加了归一化/padding 的内存搬运。

**结论：维持现在的逐裁剪循环，不要做批处理改造。** 这条本身是个有价值的负面结果——它避免了约 1–2 小时的无用改造，也说明"API 支持"不等于"有加速"。

**顺带得到一个佐证 P1-5/P1-6 的硬证据**：同一份 39 张串行的活儿，两次独立测量的绝对耗时是 **3.89 s 和 5.27 s**（相差 35%）。**这正是"耗时数字必须预热 + 重复 + 报中位数"的实证依据**——报告里的 82.0 s / 11.1 s 这类单次数值不具备可复现性。

## 实测（第 9 轮）：端到端错误分类 —— 「漏检」里 61% 其实是框对不上

给 `evaluate_end2end.py` 加了 `--dump-lines`（行级明细：读对/读错/漏读/多余/忽略 + 每行的

**297 个有效文本行的四种结局**：

| 结局 | 行数 | 占比 |
| --- | --- | --- |
| **读对** | 107 | **36.0%** |
| **读错**（匹配上但文本不一致） | 61 | 20.5% |
| **漏读**（无任何预测框匹配） | 129 | 43.4% |

**起因**：本轮做分辨率实验时整批结果为 0，排查发现读图全失败。

```python
img = cv2.imread(str(path))

```

于是：

  迁移到 ASCII 路径后这条不再触发，但**代码缺陷依然存在**，应改用 `imread_unicode`。

## 附带：`sort_boxes` 的一个继承性怪癖（建议保持原样）
